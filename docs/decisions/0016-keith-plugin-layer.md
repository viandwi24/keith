# 0016. The Keith plugin layer: one operations registry

Status: Accepted (2026-11-08). Fulfils the plugin promise of ADR-0003 and ADR-0007. Plan: docs/plans/done/P16-keith-plugin-layer.md. Amended by ADR-0027 §3 (migrations may run at start, after a backup) and ADR-0038 (proposed: extension points; §5 a plugin may serve the static files of its web apps).

## Context

Features are brain-region modules wired by hand (`modules/wernicke-broca/agent.ts` lists every plugin). `packages/host/src/index.ts` is empty and `plugins/` holds
a README; `scripts/check-imports.ts` already limits `plugins/*` to `@keith/host` and `@keith/contracts`. The owner wants big features (Notes, Reminders first)
installed in the core, behaving like apps, with built-ins using exactly the shape a later plugin would use. eharness already has plugins (`definePlugin`, tool
sources, hooks, services) but its `HarnessContext` carries only an opaque principal, and its tool function form is resolved once per session while the principal
is a live per-turn getter. Without a host, each feature would reinvent actor resolution, authorization, rate limits and audit.

## Decision

1. **Keith has its own layer.** `defineKeithPlugin({...})` in `packages/host`, compiled by an adapter into an eharness plugin plus a tool source (name prefix
   `k-`). Plugins live in `plugins/<id>/` with a fixed layout (`plugin.ts`, `operations/`, `schema.ts`, `migrations/`, `config.ts`, tests). Built-ins load through
   the same code path; Notes and Reminders are plugins, not brain-region modules.
2. **The operations registry is the centre.** A plugin declares operations: name, zod input and output, required permission (a capability or a resource bit),
   `audience` (`user` by default; guests and public only when `audience: 'public'` is written), optional `risk`, optional `review`. From one declaration the host
   derives the AI tool (`<plugin>_<op>`), the HTTP route (`/plugins/<id>/<op>`) with OpenAPI generated from the zod schemas, the inter-plugin call, and the data a UI uses.
3. **One guard for every call:** actor -> audience -> capability -> ACL (ADR-0015) -> review requirement -> rate limit -> audit -> run. No path (tool, route, call)
   skips it.
4. **A Keith context per call.** `k` has `actor` (`user | guest | system`), `session`, `acl`, scoped `db` or `kv`, `config`, `audit`, `clock`, `schedule`, `services`,
   `call`. It is built inside each execute call from the live principal, never at session open, and the actor is re-read from the database (status, role).
5. **Services and events, no sockets.** `provides` and `requires` give typed services; plugins emit typed events on the existing activity feed (filtered per actor).
   No free-form plugin websockets or routes outside the registry.
6. **Isolation tier T1.** Plugins are trusted code the owner installs; this is not a sandbox and is documented as such. A subprocess or MCP tier is a later ADR.
7. **Storage.** Tables are named `plg_<id>_*`. Migrations are generated by drizzle-kit into `plugins/<id>/migrations`, applied only by `bun run db:migrate` (never at
   boot, like the core), each plugin with its own migrations table (`migrationsTable`; the `MigrationConfig` type in drizzle-orm 0.45.4 has it), and `assertMigrated`
   checks every plugin. A plugin never alters core tables and references people by plain text id.
8. **Capabilities.** A plugin registers its capabilities into the closed set at install; the owner sees them. Role defaults for a plugin capability are declared by the plugin.
9. **Pending owner review is a host facility.** An operation may declare `review`; when it applies, the host stores the validated input in `owner_reviews` instead of
   running it, shows it to the owner as data (the owner's attention list and CLI), and on approval replays it through the guard as the requester. It lives here, not in the
   ACL: it needs the registry (operation names, input schemas) and the audience rules.
10. **Built-ins.** Notes: private by default, shareable per ADR-0015. Reminders: the owner creates for anyone directly; a user for themselves directly; user A for user B goes
    to the review queue and takes effect only after approval; the **creator pays** for the turn that fires it; a fire for a creator who lost the right is skipped and audited.

## Consequences

- A feature needs one folder and one manifest; adding an interface (route, tool, UI data) is not extra code.
- The adapter owns authorization, so a careless plugin cannot forget it; a conformance test (ADR-0015 leak kit) runs on every plugin's operations.
- Restart-only changes: enabling or disabling a plugin takes effect at the next boot (amended at P16 step 10: the setting is read once at load, which keeps the loader free of live unloading; the operator output says so), and so do installing or updating.
- Two permission systems meet: oRPC procedures keep their closed capability list; plugin operations use the same table plus registered ids.
- Not moved: auth, people, thalamus, amygdala, motor, nodes, providers, resume, brain-events, audit and cortex stay platform modules (a host that depends on plugins would be a cycle).
- Revisit when a third-party plugin is wanted (tier T2), or when a second app needs the operations registry (then move it to eharness under the rule of two).
