# Delivery

Code: `apps/core/src/modules/delivery/` (service, front route, planner, digest, presence feed, removal registry hook). Table and repo:
`packages/db/src/schema/delivery.ts`, `packages/db/src/repos/deliveries.ts` (`db.md`). Contract:
`packages/contracts/src/delivery.ts`. Decisions: ADR-0024 §5 (one delivery service, exactly once by run id), ADR-0027 §16
(exactly once, `lastSlot` in the fire transaction, the boot tick, fire counters, failures reported to the creator).

## Purpose

When the core has something to tell a person (a due reminder, later a protocol step), it goes through this one service. It
delivers exactly once for a run id, retries when the front agent is briefly unreachable, and tells the creator when it finally
could not deliver. It has one seam where routing by presence (P27) and protocol `notify` steps (P28) plug in later.

## Contracts

`packages/contracts/src/delivery.ts` (zod; exported from `area-runtime.ts`):

- `DeliveryRequestSchema`: `id` (the run id, 1 to 200 characters), `source` (`plugin:reminders`, `admin` for the owner's test notice, later `protocol:<id>`), `to`
  (person id), `billTo` (optional payer), `name` (the `eh.event` name), `text` (1 to 4000), `data` (optional JSON), `needs`,
  `onFailure` (optional failure notice).
- `DeliveryNeedsSchema`: `mode` (`wake` default: start a turn; `note`: store it, no turn, no cost), `capabilities` (at most 5 client
  capabilities the route must offer, all of them), `fanout` (`best` default: first route that works; `all`: every route the planner
  returns), `urgency` (`normal` default, `high`), `immediate` (optional: the person asked for this just now, e.g. a room handoff of their own request, or set it for this time, e.g. a
  reminder through `ctx.wake({ immediate: true })`; never held).
- `DeliveryFailureNoticeSchema`: `to`, `text` (at most 1000), `key` (at most 120).
- `DeliveryOutcomeSchema`: `delivered` `{ route, attempts }`, `queued` `{ reason: 'unavailable', nextAttemptAt }`, `failed`
  `{ reason, attempts }`, `held` `{ reason: 'busy' | 'away' | 'out' | 'offline', until? }` (kept for the return digest). Reasons of a failure: `budget`, `unavailable`, `recipient-gone`, `no-route`.
- `DeliveryFailedRecordSchema`: the activity record `delivery.failed` (see "Failure notice").
- `AdminNoticeSendSchema` `{ person, text }` (text 1 to `NOTICE_TEXT_MAX`, 500) and `AdminNoticeSentSchema` `{ id, to, outcome }`: the
  owner's test notice (see "Owner's test notice").

## Data

Table `deliveries` (migration generated by drizzle-kit, additive):

| Column | Notes |
| --- | --- |
| `id` (PK) | the run id; a second create with the same id returns the stored row: the exactly-once guard |
| `source`, `recipient_id`, `bill_to`, `name`, `needs` (JSON), `data` (JSON) | the request |
| `text` | blanked (`''`) when the row becomes `delivered` (text is kept only while the delivery is pending) |
| `report_to`, `report_text`, `report_key` | the failure notice, null when none |
| `status` | `pending`, `held` (kept for the return digest), `delivered`, `failed` |
| `reason`, `attempts`, `next_attempt_at`, `route` | outcome fields; a held row has `reason` `held:<why>` and no `next_attempt_at`; a row released by a digest has route `digest` |
| `created_at`, `updated_at` | epoch ms |

Index `(status, next_attempt_at)`. Rows `delivered` or `failed` are purged 7 days after `updated_at` by the prune tick
(`platform/retention.ts`, `deliveriesMs`, audited as `data.pruned { table: 'deliveries' }`).

## Service

```ts
interface DeliveryRoute {
  id: string // 'front'
  companion?: boolean // a Web Push (push.md): runs in its place, never decides (see below)
  send(request: DeliveryRequest, ctx: { attempt: number }): Promise<RouteResult>
}
type RouteResult = { ok: true } | { ok: false; reason: 'budget' | 'recipient-gone' | 'unavailable' }
type RoutePlan = DeliveryRoute[] | { hold: { reason: 'busy' | 'away' | 'out' | 'offline'; until?: number } }
interface RoutePlanner {
  plan(person: string, needs: DeliveryNeeds): Promise<RoutePlan> // routes ordered best first, or a hold
}
```

`createDelivery({ deliveries, planner, audit, activity, isActive, now, retryMs, tickMs, warn, front, notify, presenceOf })` returns `{ deliver, release, tick, start, stop }`.
`deliveries` is the repo of `db.md`; `isActive` (default: everybody) is the person check; `retryMs` is `[60_000, 300_000, 1_800_000]` (1, 5 and 30 minutes); `tickMs` is 30 000.

- `deliver(request)`: validates the request, creates the row (an existing id returns its stored outcome and sends nothing), then
  runs one attempt. The outcome is returned.
- An attempt asks the planner for routes and tries them in order. With `fanout: 'best'` it stops at the first `ok`. With
  `fanout: 'all'` it tries every route and is `delivered` when any is `ok`.
- A **companion** route (`companion: true`, the Web Push of `push.md`) is sent in its place in the plan but never decides: its answer is ignored (a throw is
  only a warning), it never counts as delivered or as a refusal, and the next route is always tried. A push therefore never replaces the front session, in
  `best` and in `all`, and the outcome's `route` names the route that did take the message.
- `budget` and `recipient-gone` are terminal: the row is `failed` at once. `unavailable` on every route schedules the next retry
  (`queued`, audit `delivery.retry`). After the last retry the row is `failed` with reason `unavailable`. An empty route list is
  `no-route` (terminal). With `fanout: 'all'` a delivery is `unavailable` (retried) when any route was unavailable, else the first terminal refusal.
- A terminal failure (also the last retry) sends the failure notice, writes `delivery.failed` and the activity record.
- `tick()` also runs the digest sweep (see "Hold and digest"). It selects `pending` rows with `next_attempt_at <= now`, at most 20 per tick, and attempts each one. `start()` runs
  `tick()` once at boot (rows left `pending` by a stopped core are retried) and then every `CoreTiming.deliveryTickMs` (30 000 by
  default). `stop()` clears the timer.
- A `hold` plan stores the row as `held` (see "Hold and digest"): no attempt, no retry timer, the text kept, audit `delivery.held`; `deliver()` answers `held`.
- The recipient is checked first: an inactive person (not `active`, ADR-0027 §15) is `recipient-gone`.

### Default route: `front`

The route is the former wake, its rules unchanged. `modules/plugins/wake.ts` is an adapter over this service and keeps no copy:

1. Budget: the payer (`billTo` or `to`) must have `FRONT_TURN_BUDGET_USD` left (`budget` otherwise). Applies to `mode: 'wake'` only.
2. `agent.session(frontSessionId(to), frontSessionOptions(id, lock))`, the shared lock, the person as principal.
3. `session.inject('eh.event', { name, text, data }, { deliver: 'next-turn', wake: needs.mode === 'wake', principal, key })`.
   `principal` is `{ id: to }`, plus `billTo` when the payer differs. `key` is the run id; a key longer than 200 characters is
   replaced by its SHA-256 hex. eharness returns the stored message for a key it has seen in the newest 200 messages, so a retry
   or a restart after a hard kill is a no-op (ADR-0027 §16). `mode: 'note'` injects with `wake: false`: stored, no turn, no budget.

### Plugin wakes (`modules/plugins/wake.ts`)

`createWake({ delivery })` maps `ctx.wake(request)` to a `wake` delivery with `source: 'plugin:<id>'`, `id` = the run id, and
`onFailure` = the request's `failureNotice`. The stored outcome maps to the plugin's `WakeResult`: `delivered` to `{ delivered: true }`,
`queued` to `{ delivered: true, queued: { nextAttemptAt } }`, `failed` to `{ delivered: false, reason }` (`no-route` is reported as
`unavailable`). A transient outage never reaches the plugin.

### Wiring and timers

`compose-delivery.ts` builds the service once in `createCore` (the `deliveries` repo, the front route over `holder.lead`, the person
check, `emit` for the failure record, the audit). `CoreTiming.deliveryTickMs` (30 000) and `deliveryRetryMs` (`[60 000, 300 000,
1 800 000]`) are the tick and the waits; tests use 20 ms and 20 ms. Boot calls `start()` after the plugins' schedules start, and
`close()` calls `stop()`. The ended rows are pruned by `pruneRetention` (`deliveriesMs`, 7 days) on the prune tick.

### Planner seam (P27, P28, P29)

`createDelivery({ planner })` takes any `RoutePlanner`. The default is `[frontRoute]`. P27 supplies a planner that orders
routes by presence (the active client, then the most recent reachable client that offers every `needs.capabilities` entry, then
the front session; `createPresencePlanner` in `modules/parietal/planner.ts`, composed in `compose-delivery.ts`). It may return an
empty list, which is `no-route`, or a `hold` (P37.4, "Hold and digest"). `singleRoutePlanner` never holds. P28's `notify` step calls `deliver()`
with `source: 'protocol:<id>'`. Neither needs a change to the service or the table. P29 fans out with `fanout: 'all'`.

## Hold and digest (ADR-0034 §6, §7)

The presence planner holds a `wake` delivery for a person who is busy, away, out or offline (docs/specs/parietal.md "Routing"); a note, an urgent delivery
and one with `needs.immediate` are never held. A held row waits in the table (`status: held`, `reason: held:<why>`), and nothing else reads it.

- **Release on return.** The core watches the activity feed (`compose-delivery.ts`, `presence-feed.ts`: a cursor over `store.read`
  of `brain.parietal.presence`, started at the newest record, polled every `min(deliveryTickMs, 5 s)`). A record whose `state` is `active` or
  `idle` calls `delivery.release(personId)`: every held row of that person (oldest first, at most 20 per digest, the rest is the next digest) is released as ONE digest.
  Release is by state, so a stated `out` or `busy` that ends (busy back to active) releases too.
- **The digest.** One wake delivery on the person's front session (`front` route: the person is the principal), run id `digest:<hash of the row ids>`
  (the inject key, so a repeat is a no-op), name `digest`. The text says how many messages were held, instructs the agent to brief the
  person in their language and address (the count first, each item in one line, then one closing line, ADR-0034 §1) and lists the items
  as `n. <name>: <text>` (each clipped to 140 characters). Then one `notify` to the person's active client when it announces `notify`
  (`Keith · <n> held messages`, best effort). Each row becomes `delivered` with route `digest` (audit `delivery.sent`, route `digest`). When the turn is refused (budget) the rows stay held.
  Releases of one person run one at a time and the rows leave `held` after the turn, so a second presence record finds nothing to release.
- **The sweep** (each tick): a person who is `active` or `idle` now (`presenceOf`) and has held rows is released (a missed presence
  record, a stated status whose `until` passed); a row held for more than 7 days (`HELD_MAX_MS`) is sent to the front session as a plain note
  (`mode: note`) and marked `delivered`, route `front`.
- **Urgent bypass.** A `high` delivery for a busy, away, out or offline person is not held: its routes are the reachable clients, the `push` routes (a Web Push, `push.md`, when the person has a subscription) and the
  front session, and the front route appends one line to the wake text asking the agent to open with one sentence saying why it interrupts.

## Failure notice

When a delivery fails terminally and `onFailure` is set, the service makes a second delivery:

- run id `report:<onFailure.key>`, `needs.mode: 'note'` (stored, no turn, no budget), `to` = `onFailure.to`, name `delivery-failed`,
  text `onFailure.text`, source `delivery`, no `onFailure` (no loops).
- The notice's row id is `report:<key>`: a second failure with the same key finds the stored row and writes nothing (once per key).
- If the creator cannot be reached either, only the audit row and a log line remain.

Activity record (no text, on the recipient's own front session, so the feed shows it to that person only):
`delivery.failed` with `DeliveryFailedRecord` `{ personId: to, deliveryId, source, reason }`. It is the source of P28's
`reminder-missed` trigger (an `event` over `delivery.failed` with `source: 'plugin:reminders'`).

## Owner's test notice

`admin.notice.send` (`keith-core notify <username> <text…>`, `core-cli.md`) lets the owner send one notice through this service to
check the client path, for example the TUI toast of a `notify` client. Owner only: `audit.read` with a step-up, as
`admin.presence.read`. The request is source `admin`, name `notice`, id `notice:<uuid>`, to the person, with
`needs` `{ mode: 'note', capabilities: ['notify'], fanout: 'best', urgency: 'normal' }`. The planner tries every client of the person
that declared `notify` first (the active one, then by last activity); when none takes it, the front session stores the note with no
turn. A TUI shows the toast `Keith · notice: <text>` and acks it. The procedure returns the run id, the person id and the
`DeliveryOutcome`; the CLI says where it went (a client id, or the front session), or why it did not arrive.

## Audit

Actor `system`, via `local`. Never text. Kinds and detail:

| Kind | Detail | Subject (`AUDIT_SUBJECT_FIELDS`) |
| --- | --- | --- |
| `delivery.sent` | `id`, `source`, `to`, `route`, `attempts` | `to` |
| `delivery.retry` | `id`, `attempt`, `nextAttemptAt` | `to` |
| `delivery.failed` | `id`, `source`, `to`, `reason`, `attempts` | `to` |
| `delivery.reported` | `id`, `to` (the creator who got the notice) | `to` |
| `delivery.held` | `id`, `source`, `to`, `reason` (no text) | `to` |
| `delivery.push` | `id`, `source`, `to`, `subscription` (the subscription id, never the endpoint), `ok`, `status` (one row per subscription pushed; `push.md`) | `to` |
| `delivery.test_notice` | `id`, `to`, `status`, `route`, `reason` (the owner's `admin.notice.send`; the actor is the owner; no text) | `to` |

Member view (`modules/audit/mine.ts`): `delivery.reported` reads "a message you set could not be delivered"; `delivery.test_notice` reads "the owner sent you a test notice"; `delivery.sent`,
`delivery.retry`, `delivery.failed`, `delivery.held` and `delivery.push` are hidden (the plugin's own rows describe the reminder).

## Removal

Pending and held rows of a removed person are registered in the removal registry (ADR-0027 §26): `keep` leaves them, `purge` deletes them,
`export` lists their ids only.

## Doctor

Check `delivery` (`keith-core doctor`): `!` when `pending` rows are older than one hour, with the count. `failed` rows of the last
7 days are listed as a hint.

## Invariants

- The same run id is sent once: a `delivered` row never sends again; the inject key covers a crash between inject and the row update.
- Text is kept only while a row is `pending`, `held` or within 7 days of its end.
- At most 20 rows per tick; after the last retry a row is final.
- Audit and activity rows hold no text.
