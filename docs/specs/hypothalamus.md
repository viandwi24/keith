## Purpose

Keith acts before it is asked, and every proactive act is a visible, pausable rule. A **protocol** is data: a trigger, conditions, a
ladder of steps and limits. A deterministic engine runs protocols and keeps their state in SQLite, so a restart resumes them. The
model is a step (`wake`), never the scheduler. The owner, and any person for their own life, can list, pause and audit protocols.
Keith may **propose** a protocol from what a person says; it is saved only when the person confirms. The **agenda** is the personal
list of what a person will do and when; presence reads it through a port and protocols may test it.

Layer (ADR-0020): `keith`-owned protocols belong to the self layer (owner); person-owned protocols and the agenda belong to the
personal layer of that person. Nothing here is loaded into another principal's model context (see "Principal and rights" and the
leak test P28.5.5).

## Terms

- **Protocol**: versioned definition of trigger, conditions, steps and limits, owned by a person id or `keith`.
- **Run**: one execution of a protocol for one trigger occurrence. Its id is the delivery key root of P25.
- **Step**: one action of a run (`notify`, `ask`, `wake`, `act`, `wait`). A step may branch.
- **Visit**: the n-th execution of one step within one run (counted per step id, for loop limits and delivery keys).
- **Pre-approval**: the owner's stored approval of an `act` step, bound to the SHA-256 of its exact input.
- **Proposal**: a definition Keith suggests; data only until a person confirms it.
- **Owner of the run**: the person a run acts for. For a person-owned protocol it is the owner; for a `keith`-owned protocol it is the
  instance owner found when the run starts (`people.owner()`, read at use), stored on the run. A later transfer does not move a run
  already started. `owner-of-run` in a step means this person.

Retention: runs and run steps are kept 90 days after `ended_at` (prune tick, audited `data.pruned`); proposals are kept 30 days after
`expires_at` (the table has no decision time, so an expiry stands in for the end); agenda items are purged 30 days after their end
(`ends_at`, or `starts_at + 60 min` when `ends_at` is null). Every table is in
the retention inventory of `db.md`.

Removal of a person (ADR-0027 §26): `modules/hypothalamus/removal.ts` registers protocols (owned by the person), their runs, proposals and
agenda rows in the P26 removal registry: `keep` moves them into the 30-day retention with the person's other data, `export` adds them to
`people export`, `purge` deletes them. `people.ts` is not edited.

## Contracts

`packages/contracts/src/protocols.ts`, all zod. Types are `z.infer` of the schemas. Names below are the export names.

### Identifiers and text

- `StepIdSchema`: `^[a-z0-9-]{1,32}$`, unique within a definition.
- `PersonRefSchema`: a person id (1 to 80 characters).
- `Text`: plain text. Notify text 1 to 500 characters, wake instruction 1 to 1000, ask text 1 to 500. A text that contains a template
  marker (`{{`, `}}`, `${`, `{%`) is refused. The engine never interpolates data into a text; a fixed text cannot become an injection channel.
- Limits of time: `MS_MINUTE = 60_000`, `MS_DAY = 86_400_000`.

### Trigger (`TriggerSchema`, discriminated by `kind`, strict objects)

| `kind` | Fields | Rules |
| --- | --- | --- |
| `time` | `cron` or `at` (exactly one) | `cron`: five fields, core zone. The minute field is a number, a comma list of numbers, or `*/n`; all forms that fire less than 15 minutes apart are refused (`*`, `*/n` with n < 15, lists with a gap < 15). `at`: epoch ms, integer. |
| `absence` | `person`, `afterMs` | `afterMs` from 1 hour to 90 days |
| `signal` | `type` (`client.connected`, `client.disconnected`, `client.active`, `device.location`, `node.event`, `activity`), `filter?` | `filter` is a flat equality map (at most 5 keys, values string up to 120, number or boolean); no code |
| `event` | `type`, `filter?`, `afterMs?` or `until?`, `guard?` | `type` is `brain.<region>.<phase>` or `delivery.failed`; the known set is checked by the authoring function. `afterMs` (0 to 90 days) and `until` are mutually exclusive. `until: { field, beforeMs }`: `field` names an integer ms field of the event payload, `beforeMs` 0 to 30 days. `guard` is a Condition. |

### Condition (`ConditionSchema`, discriminated by `kind`, strict, no expression language)

| `kind` | Fields | True when |
| --- | --- | --- |
| `all` | `of` (1 to 8 conditions) | every item is true |
| `any` | `of` (1 to 8) | one item is true |
| `not` | `of` (one condition) | the item is false |
| `time.between` | `from`, `to` (`HH:MM`, 24 h) | the core's clock, in its zone, is in `[from, to)`; `from > to` wraps midnight |
| `presence` | `person`, `in` (1 to 5 of `active`, `idle`, `away`, `busy`, `offline`) | the presence state of the person, as the disclosure rule releases it to the run (the state the owner-of-run may read) |
| `agenda.busy` | `person` | a confirmed item of the person covers the evaluation time |
| `signal.since` | `person`, `ms` (1 minute to 90 days) | the newest sign of the person (`lastSign`) is no older than `ms` |
| `signal.sinceRunStart` | `person` | the newest sign of the person (`lastSign`) is strictly later than the run's `startedAt`; false at a start (no run yet) and when there is no sign. Read only inside a run (`cancelWhen`, condition branches) |
| `budget.remaining` | `person`, `usdAtLeast` (0 to 10) | the person's budget has at least this left |
| `approval.pending` | `approvalId?` (absent: the approval an event trigger names, its run ref `approval:<id>`, `gate.ts`; elsewhere never pending) | the approval is still pending; the value returned to the trigger is its current `expiresAt` (see "Triggers") |

### Step (`ProtocolStepSchema`, discriminated by `kind`, strict; type `ProtocolStep`)

Every step has `id`, optional `next` (a step id or `end`), optional `branches` (at most 4 entries), and its own fields:

| `kind` | Fields | Outcomes that branch |
| --- | --- | --- |
| `notify` | `to` (`owner-of-run` or a person id), `text`, `needs?` (client capabilities, at most 5), `urgent?`, `channels?` (`best` default, or `all`) | `ok`, `failed` |
| `ask` | `to`, `text`, `options?` (1 to 5 ids `^[a-z0-9-]{1,32}$`), `timeoutMs` (1 minute to 7 days), `channels?` (`best` default, or `all`, as `notify`) | `answer:<option>`, `timeout` |
| `wake` | `to` (`owner-of-run` or a person id), `instruction`, `urgent?` | `ok`, `failed` |
| `act` | `operation` (`{ kind: 'node.capability', node, capability }` or `{ kind: 'plugin.operation', plugin, operation }`), `input` (JSON, at most 8 KB) | `ok`, `failed` |
| `wait` | `durationMs` (1 minute to 30 days) | none (continues to `next`) |
| `system` | `action` (`succession.begin-grace`, `succession.open-claim` or `succession.cancel`) | `ok`, `failed`, `refused:no-handler` |

`channels` of `notify` maps to the delivery request's `needs.fanout` (P25, delivery.md): `best` stops at the first route that works,
`all` asks every route the planner returns (every connected client of the person, a queued client for its next connection, and the
front session). Default `best`, as before.

`system` runs a coded action of the core, never a plugin or a node. Only the built-in `owner-absence` may hold one: `authorDefinition`
refuses a `system` step for every other definition (`author-rule`) and the proposal schema refuses it (`invalid`). The engine hands it
to the step runner's `system` handler (`StepRunnerDeps.system`, wired by P29.2.4); without a handler the step is `refused:no-handler`
and the run fails. A replayed `started` system row is run again, so each handler is idempotent on its own state row (P29.2.4).

`urgent` is accepted by the schema only on `notify` and `wake`, and only as a value the authoring function may allow (owner, see
"Authoring"). `to` on `wake` is needed because a `keith`-owned protocol never implies a person.

Branches: `{ when, condition?, goto }`. `when` is `answer:<option>` (an `ask` only, the option must be in `options`), `timeout` (an `ask`
only), `ok` or `failed` (`notify`, `wake`, `act`), or `condition` (any step; `condition` is required and is tested first, in order).
`goto` is a step id or `end`. Without a matching branch the step's `next` is followed; without `next` the run ends (`done` for an `ok`
outcome, `failed` otherwise).

### Definition (`ProtocolDefinitionSchema`)
`{ trigger, conditions: Condition[] (at most 8, default []), steps: Step[] (1 to 40), limits: Limits (default), start: StepId }`.

Refinements, each with an error path: `start` is a step id; step ids are unique; every `next`, `goto` and `branches[].goto` is a step id or
`end`; every `answer:<option>` names an option of its `ask`; a `condition` branch has a condition; an `ask` without `timeout` branch ends
the run `expired` when the timeout comes (documented in "Engine").

### Limits (`LimitsSchema`, defaults applied)

| Field | Range | Default | Meaning |
| --- | --- | --- | --- |
| `maxRunsPerDay` | 1 to 20 | 3 | runs of this protocol per UTC day; the 4th start of the default is refused (no run row) |
| `budgetUsdPerRun` | 0 to 0.5 | 0.05 | budget of one run; only `wake` costs |
| `maxSteps` | 1 to 100 | 100 | step executions per run; more ends the run `failed` with `limit` |
| `maxVisits` | 1 to 30 | 30 | executions of one step per run; more ends the run `failed` with `limit` |
| `quietHours` | `{ from, to }`, optional | none | `notify` and `wake` inside it wait for its end unless `urgent` |
| `cancelWhen` | Condition, optional | none | re-evaluated at every tick of a waiting run and at every transition of a running one; true ends it `cancelled` |
| `onCancel` | step id, optional | none | run once when `cancelWhen` holds, before the run ends; the end stays `cancelled` whatever that step does |

`onCancel` (P29): the run's state holds the cancel reason while the step runs (kept in the `answers` JSON under a reserved key, so no
migration is needed). The step's chain is not checked against `cancelWhen` again. Its end, `done`, `failed` or `expired`, is written as
`cancelled` with `reason: cancelWhen`. Without `onCancel` the run ends `cancelled` at once, as before.

`definition`, `reason` (at most 200), `status`, `createdAt`, `expiresAt`.

## CLI (`cli/protocols-command.ts`, P28.3.3, P28.3.5)

`keith-core protocols list | show <id> | pause <id> [--until <time> | --hours <n>] | resume <id> | delete <id> [--yes] |
runs <id> [--limit n] | settings get | settings set [...]`, one command with its verbs as subcommands (`settings` reads its
action from its positionals). Each verb calls `protocols.*` through the owner socket and adds no rule of its own: the RPC decides. `pause` without an end calls `protocols.setEnabled(false)` and `resume` calls `protocols.get`, then
`setEnabled(true)` if off and `pause(null)` if a pause is set. `delete` reads the protocol first (an unknown id is refused) and
asks y/N outside a terminal only with `--yes`. Its output names the protocol, never a message text or a step input. The
parity table of `cli-rpc-parity.test.ts` lists the verbs; an own-protocol procedure is `chat` with no step-up, and only
`protocols.settings.set` is a step-up (`settings.manage`).

## Triggers (`triggers.ts`)

- **`time`** is a schedule row in `eh_schedules` (the eharness scheduler that plugins already use, `modules/plugins/schedule.ts`).
  Session id `protocol:<id>`, payload `{ protocolId, version }`. Catch-up is the latest slot only (ADR-0027 §16 pattern). The fire id is
  the run's `trigger_ref`. A one-shot `at` removes its schedule after it fires. No second timer system.
- **`absence`** is armed for each `person` of an absence trigger. The engine reads `lastSign(person)` each tick. When
  `now - lastSign >= afterMs` a run starts with `trigger_ref = absence:<lastSignAt>`. One run per absence period: a new sign moves the anchor
  and arms a new period. Never armed while the person has no sign at all (a new person does not start as absent).
- **`signal`** matches rows of the presence signal store (P27, `presence_signals`) newer than the cursor, by `type` and the flat
  `filter`. The trigger ref is `signal:<signalId>`. A signal rule never matches a row older than its save; a stale cursor is moved
  up to the oldest save of the signal rules before the read, so a rule saved after a quiet period replays nothing.
- **`event`** matches rows of the activity feed (`events` table, `activity()` store) newer than the cursor, by `type` and `filter` on the
  payload. The trigger ref is `event:<seq>`. Without `afterMs` or `until` the run starts at once. With `afterMs` the run starts in
  `waiting` with `wake_at = event.at + afterMs`. With `until` the run starts in `waiting` with `wake_at = event[field] - beforeMs`.
  When the wake time comes the guard is evaluated; a false guard ends the run `skipped`. The guard `approval.pending` returns the
  approval's current `expiresAt`: if `expiresAt - beforeMs` is later than now the run waits again until that time (a TTL change moves the
  ping; it never makes it early or late). A pending approval whose `expiresAt` is past ends `skipped`.
  **The built-in `approval-stale` takes its offset from the setting** (`approvals.pingBeforeHours`, read through the injected
  `pingBeforeMs` port each time its trigger is evaluated): `evaluatedTrigger` (`builtins.ts`) replaces the
  stored `until.beforeMs` of a protocol whose `builtIn` is `approval-stale`, both when the run is started (`wakeAt`) and when its
  guard is read at the wake time (`drive.ts`). The stored definition is never rewritten, so an owner's other edits to the
  built-in survive. Any other protocol keeps its stored `beforeMs`.
  **Limit:** a pending ping moves at its wake time only. A ping or TTL change that moves the due time *earlier* than the stored
  `wakeAt` is applied when the run is next woken, so that ping comes late, not early (no re-arm of waiting runs yet). A change
  that moves it later is applied at the wake time, as above.
- **Cursor**: one settings value `protocols.cursor` `{ events: seq, signals: { at, id } }`, read once at the first tick and kept in
  memory (only this module writes it), advanced in the same transaction as the runs it started. It is written only when it advanced.
  A re-read after a restart starts nothing (the unique `(protocol_id, trigger_ref)` guard).
- **Built-in event `delivery.failed`** (P25 record, `DeliveryFailedRecordSchema`): payload `{ personId, deliveryId, source, reason }`. Its
  trigger ref is `delivery:<deliveryId>`, so one failed delivery makes one run.

Implementation notes (P28.2.5, `triggers.ts`):

- The time schedule id is `protocol:<id>:v<version>` (one per version; a new version removes the old row), session `protocol:<id>`,
  catch-up `once`. The scheduler sees only `protocol:` rows through `protocolScope`, so it never claims a plugin's row. The plugin
  scheduler sees the same table through `pluginScope` (`modules/plugins/schedule.ts`, wired in `compose-plugins.ts`, P28.2.6): it
  never reads, lists or claims a `protocol:` row, so a protocol one-shot is not consumed by a plugin's timer (test in `schedule.test.ts`).
- The trigger's `guard` (`gate.ts`, P28.2.6): the driver reads it when a run first moves, that is while the run sits on its start
  step with no visit (at its wake time, or at once for a run without delay). A false guard ends the run `skipped` (`reason: guard`).
  `approval.pending` answers "pending, but due later": the run waits again until `expiresAt - beforeMs`; an approval no longer pending
  skips it. A run has no flag of its own for this: the state says whether it has moved.
- A fired one-shot keeps its row while its version is wanted: that row is the idempotency record of the slot.
- Absence: the period is anchored on `max(lastSign, savedAt)` of the version, so a sign from before the protocol existed does not fire
  it at once. A period is consumed whatever the start answers (`refused` is not retried every tick).
- A record or signal older than the version's `savedAt` never matches it. A person-owned protocol matches only records and signals of its
  owner (a `keith` protocol names its person through the filter or the step).
- Cursor: on the first tick of a store the cursor starts at the feed head and at `now` for signals (no replay of history). A cursor
  below the feed's pruned mark moves up to it. A kind with no protocol listening is not read and its cursor is not written; a
  protocol saved later does not replay the backlog, because its `savedAt` filter drops older records (the event cursor may still
  catch up over a few ticks after a long quiet period). The cursor is saved after each start, so a crash between two starts re-reads at most the last one; the
  `(protocol, ref)` guard makes that re-read a `duplicate`. Not one transaction across the engine port: the guard is the guarantee.
- Paused and disabled protocols are decided by the engine (`RunStarter` answers `refused`); triggers do not check the pause.
- `signal` needs a `since(cursor, limit)` read of `presence_signals` (the P27 repo has `newest` only); the wiring adds it.

## Conditions (`conditions.ts`)

Pure: `evaluateCondition(condition, { viewer, ports })` reads only the injected ports and returns `Promise<boolean>`. No I/O in the file.
The condition is validated with `ConditionSchema` first; an unknown `kind` or a bad field throws before any port is read. `viewer` is
the run's person: `presence` is read as that viewer.

`ConditionPorts` (defined in `conditions.ts`; each is an adapter over the owning region, wired in P28.2.6):

- `clock: { now(): number; timeZone: string }`: `time.between` reads the wall clock in the core's zone.
- `presence(viewer, subject): Promise<PresenceState | null>`: the state the viewer may read, released by parietal's disclosure rule
  (`disclosedFor`). `DisclosedLine` carries a level and a line, not a state, so the adapter returns the state only when the level is
  `state` or `detail`, and `null` otherwise. A condition never sees a note, a client id or a message.
- `agenda.confirmedNow(person, now)`: a confirmed item of the person covers `now`.
- `lastSign(person)`: parietal's `lastSign`; `signal.since` is true when `now - lastSign <= ms` (no sign: false); `signal.sinceRunStart`
  is true when `lastSign > run.startedAt` (the condition env carries `runStartedAt`; absent at a start, so false there).

### Sign of life (`sign-of-life.ts`, P29.2.2)

`createSignOfLife({ lastSign, pausedUntil })` is the owner's sign of life as one port, the shape of `lastSign` above and of the
triggers' `LastSignPort`. It adds no tracker: `lastSign` is parietal's port (the signals `activity`, `client.active`, `client.connected`
of the person, `SIGN_OF_LIFE_SIGNALS`, pinned equal to parietal's `LAST_SIGN_TYPES`). The one added rule is the pause: the sign of a
person is the later of parietal's sign and `pausedUntil(person)` (null when none; the succession setting answers only for the owner).
A pause counts as a sign until it ends, so the silence is counted from its end; a pause that ended long ago does not lower a newer sign.
Not signs: `node.event`, a heartbeat without `active`, `client.disconnected`, reads of presence, and any signal of another person (a heir,
a delegate). An offline command writes no signal. `sign-of-life.test.ts` writes these through the real parietal service and repos.
- `budget.remaining(person)`: USD left, compared with `usdAtLeast` (at least).
- `approvals.pending(approvalId)`: the record as stored, or null. A record counts as pending only while `expiresAt > now`
  (`pendingApproval`, also used by triggers to read the current `expiresAt`).

Semantics: `all` and `any` stop at the first decisive item. `time.between` is `[from, to)`; `from > to` wraps midnight (quiet
hours 22:00 to 07:00); `from === to` is an empty window. `minutesOfDay(epochMs, timeZone)` is the wall-clock minute in the zone.

## Engine (`engine.ts`, `steps.ts`)

### Tick

One interval, `protocols.tickMs` (see "Settings"). The tick returns at once when nothing is due: no run waiting with `wake_at <= now`,
no armed absence trigger due, no new feed row. The set of enabled protocols is cached in memory (`catalog.ts`); the protocol service and
the removal of a person call `changed()` after every write that moves an enabled version, so an idle tick reads no protocol row. With
no enabled protocol the trigger pass ends at once (no read, no write, no schedule scan). With a listener: a time protocol scans its
schedules, a feed rule reads one head (`lastSeq`) and reads the rows only when the head is past the cursor, a signal rule reads its
signals. Each tick, in order:

1. evaluate `absence` triggers;
2. drain new feed events and signals after the cursor (`protocols.cursor`);
3. advance every run with `wake_at <= now` (oldest first), one step per advance;
4. evaluate `cancelWhen` of every running or waiting run.

Ticks never overlap (a flag in the engine); a tick that throws logs and the next tick continues. Implemented in `engine.ts`:
`tick()` first re-checks `cancelWhen` of the runs in the engine's watch set (the waiting runs, filled when a run is written
`waiting`; `watchWaiting(runs)` seeds it at boot), then takes the due runs (`claimDue`, at most `tickLimit`, 50) and drives each
until it waits or ends. An idle tick with no enabled protocol is one `claimDue` query and nothing else (tests: `idle.test.ts`, with counting fakes). With a feed rule enabled (the built-in `approval-stale` and `reminder-missed` are) it adds one `lastSeq` head read. The absence, signal and event triggers and
the schedule are P28.2.5. The boot recovery is `recover()` (see "Restart"); the timer that calls the tick is in
`compose-timers.ts` (see "Wiring").

### Starting a run (exactly once)

`start({ protocolId, trigger, triggerRef, startAt? })` (`engine.ts`) reads the protocol (missing, disabled or paused is `off`, no
row). The run id is `runIdFor(protocolId, triggerRef)`: a digest, so a re-fire has the same id and the id is also the delivery
key root. A stored run of the same `(protocol_id, trigger_ref)` answers `exists` and nothing else happens. The definition's
top-level `conditions` are evaluated before the insert (viewer: the run's person, or the owner for a `keith`-owned run): one
false ends the run `skipped` at once (the row is written, no step row). `startAt` in the future creates the run `waiting` at that
time with the start step pending. Otherwise the run is inserted `running` and driven at once. Same exactly-once rule; the insert
is the guard. `maxRunsPerDay` (the protocol's limit) and
`maxPerPersonRunsPerDay` (the caps of "Settings") are counted in the same transaction; a refused start writes no row and the audit row
`protocol.run.refused` with `reason: 'daily-limit'`.

### Advancing a step

Before a step's side effect the engine, in one transaction, writes the `protocol_run_steps` row with outcome `started`, increments
`visits[step]` and sets the run `running`. After the side effect it settles that same row (`ok`, `failed:<reason>`,
`refused:<reason>`) and writes the next step pointer (or the end) in one transaction, so one row is one execution. A row that
stays `started` is a step in flight at a crash (see "Restart"). An `ask` writes its `open` answer state and `wake_at` in that
second transaction, after the question is delivered. A step row for `answered:<x>` or `timeout` is appended when the answer or
the deadline arrives. The `protocol.run.step` audit row and `brain.hypothalamus.step` event follow each settled or appended row
(not the `started` one). Every transition is a single write, so a crash leaves either the old state or the new one.
A quiet window defers a `notify` or `wake` by writing `waiting` with `wake_at` = the window's end, without a row or a visit.

- `notify`: `deliver()` of P25 with `source: 'protocol:<protocolId>'`, `name: 'protocol.notify'`, `needs.mode: 'note'`,
  `needs.capabilities` from the step, `urgency` `high` when `urgent`, id `<runId>:<stepId>:<visit>` (the step key). `ok` when
  delivered or queued; `failed:<reason>` otherwise; `refused:person-inactive` when the recipient is not active. Implemented in
  `steps.ts` (`createStepRunner`), the delivery port is `deliver-port.ts`.
- `wake`: `deliver()` with `needs.mode: 'wake'`, `name: 'protocol.wake'`, the fixed instruction as `text`, id `<runId>:<stepId>:<visit>`,
  `to` the step's person (`owner-of-run` resolves to the run's person). Checks the person is active (`refused:person-inactive`), then
  the budget: the run's `costUsd` plus `WAKE_COST_USD` (0.02) must stay within `budgetUsdPerRun` and the person must have
  `WAKE_COST_USD` left (`refused:budget`). A refused budget sends the person one note `protocol.notice` with id
  `<runId>:<stepId>:budget` (once per step). `ok` adds `WAKE_COST_USD` to the run's `costUsd`. `billTo` is not set: the recipient
  pays, which is the run's person in every case the authoring rules allow.
- `ask`: delivers the question as a note `protocol.ask` with `data: { runId, step, options }` (the card of the chat), id = the
  step key. A failed delivery is the step's failed outcome; otherwise the run is set `waiting` with `wake_at = now + timeoutMs`. The
  answer arrives through `protocols.answer` or the agent tool `protocol_answer` (the run's person only). An answer ends the wait, follows
  the `answer:<option>` branch, or `next`. The wake time ends with the `timeout` branch; without one the run ends `expired`.
- `wait`: sets `waiting`, `wake_at = now + durationMs`, then `next`. A `wait` with no `next` ends the run `done` when it wakes.
- `act`: see "act" below.

Quiet hours: a `notify` or `wake` whose time falls in `limits.quietHours` (and is not `urgent`) does not start; the run waits until the
quiet window ends (`wake_at`), without a step row. `urgent` is honoured only where the authoring function allowed it.

Limits: each execution counts into `maxSteps` and `visits`; over either the run ends `failed` with `detail.limit`. A `wait` back to a
`notify` (a daily check-in) is a loop like any other and is bounded by `maxVisits`.

Branch and end rules: see "Step". A run ends by setting `status`, `ended_at` and a `protocol.run.end` audit row with the status.

### `act`

Code: `act.ts` (`createAct({ nodes, plugins })`, passed to `createStepRunner`). The outcomes:

- `node.capability`: the capability must be in the static table (`capabilityRisk`, `motor.md`), else `refused:risk`. The node must be
  known to the registry (`find`), else `failed:unknown-node`. `shell.exec` on a node whose `allowShell` is off is `refused:risk` (the
  motor's shell rule, before anything is asked). The stored input must parse with the capability's schema, else `failed:invalid-input`.
- A capability above `read` (`shell.exec` is `destructive`) needs a pre-approval: an `approvals` entry of this step whose `hash` is
  `actApprovalHash(operation, input)` of the stored operation and input. Otherwise `refused:pre-approval`, and the call never happens.
- Then `nodes.invoke(node, capability, input, { timeoutMs })` with the motor's 120 s limit. `ok` settles the step with `ok` and the
  detail `{ node, capability, exitCode? }`; a failure settles `failed:<code>` (`offline`, `timeout`, `refused-by-policy`, ...).
- `plugin.operation`: the operation's declared risk (`read`, `write`, `dangerous`) is read from the loaded plugin; unknown is
  `failed:unknown-operation`. Anything above `read` needs the same pre-approval (`refused:pre-approval`). The call runs as the
  owner (`actor` = the owner's person id) through the plugin's guard, so ACL, status, capability and audience are checked as for a
  person; a refusal of the guard is `failed:<code>` (for example `failed:forbidden`).
- Output of a call is never stored or put in the detail (ids, lengths and codes only).
- The pre-approval is the owner's approval, recorded at save time for this exact operation and input, and it replaces the live
  `user-approval` that `tool.approve` would ask for, because no person is present when a protocol runs. The static table still decides
  which operation needs it, so a `read` capability never does. A changed input or operation is another hash: refused.
- Crash rule: the `started` row of an `act` is written before the call. After a restart a `started` `act` row without a result is never
  repeated: its outcome becomes `unknown`, the run ends `failed`, and the owner is told with the keyed notice
  `<runId>:unknown` (`drive.ts`, `writer.ts`; the engine never calls `act.ts` for it). The owner notice is sent before the run is
  written as ended, so a crash in between sends it again with the same key, and the delivery service sends it once.
- Who may run an `act` (P28.2.6): only a protocol the owner owns or a `keith`-owned one. A member's protocol refuses every `act`
  with `refused:risk`, read capabilities included; nothing is called.
- Audit (P28.2.6, row written by `act.ts` through `ports.audit`, kind `protocol.act`): every execution that reaches its call writes one
  row with `runId`, `step`, the node and `capability` (or the plugin and `operation`) and `hash` = `actApprovalHash(operation, input)`.
  Never the input, never the output. A refused act writes no `protocol.act` row (its `protocol.run.step` row says why).
- The rule this exception lives under: `motor.md` "Invariants" (`shell.exec` waits for the owner's approval) and ADR-0024 §3. An `act`
  with its owner's stored pre-approval of the exact `{operation, input}` runs without a live `user-approval`; a changed input is refused.

### Restart (`engine.recover()`)

`recover()` runs once at boot, before the tick timer starts (`compose.ts`, through `compose-protocols.ts`):

1. `watchWaiting` seeds the `cancelWhen` watch with every `waiting` run whose version has a `cancelWhen`.
2. Every `running` run left by the crash is driven again (`drive`). `wake_at` is absolute, so an overdue `waiting` run advances at the
   first tick, not at boot.

Schedules are re-armed and the cursor re-read by the triggers at their first tick (`lastSignature` is unset, so `reconcile` runs; the
cursor is stored in settings and read at each use). The engine's steps:

- `started` `notify` and `wake` rows are replayed with the same delivery key `<runId>:<stepId>:<visit>`: the P25 service returns the stored
  outcome, so nothing is sent twice.
- `started` `act` rows become `unknown` as above.
- `started` `ask` (the question delivered, the row not updated) is replayed with the same key; a waiting `ask` keeps its deadline (`wake_at`).

### Wiring (`compose-protocols.ts`, `compose-timers.ts`, P28.2.6)

`createProtocols(wiring)` builds the engine, the triggers and their ports over the real regions. It is called in `compose.ts` after
the front region (nodes, plugins) and the delivery service. Nothing reads the owner at boot: `ownerOf` (`people.owner()`) is read at
use, by a run start (the run's person), an `act` step (the actor and the owner check, per step) and the unknown-act notice; a transfer
of the owner role (P29) applies to the next start and step. The protocol catalog is created by the composition root and shared by the
service, the removal hooks and the engine. The adapters:

- `presence(viewer, subject)`: `parietal.disclosedFor(viewer, subject)`; the state is released only at level `state` or `detail`,
  otherwise `null`. Never a note, a client or a message.
- `agenda.confirmedNow`: `agendaRepo.busyAt` (a confirmed item only).
- `lastSign`: parietal's `lastSign`. `budget.remaining`: the budget's `remainingUsd` (no limit = infinite).
- `approvals.pending(approvalId)`: the attention queue (`listAttention` over every person's front session, the same read as the expiry
  sweeper); `expiresAt = createdAt + approvals.ttlMs()`, so a TTL change moves it at the next read.
- `signals.since`: `presenceSignalsRepo.since` (P28.2.6 added it; read only).
- `feed`: the activity store (`read`, `lastSeq`, `prunedThrough`); the catalog reads the enabled protocols each tick and parses a
  definition only when the set of (protocol, version) pairs changes.
- `deliver`: the delivery service (P25). `isActive`: `countsFor('route', status)`. `act`: `createAct` over the node hub and the plugin
  host (`guard.run` as the owner, session kind `schedule`).
- `transaction`: `sqlite.transaction(fn).immediate()`.

The tick: one self-re-arming timer (`createProtocolTimer`) that reads `protocols.tickMs` before each arm (a changed setting applies
without a restart) and runs `triggers.tick()` then `engine.tick()`. Ticks never overlap. `close()` clears the timer and waits for a tick
in flight, so a graceful stop never cuts a step in half.

Accepted window (documented, see plan Risks): a crash between two writes costs at most one repeated `wake` turn; the core is one process
per data dir (`core.lock`).

## Principal and rights

- A run belongs to `person`: the owner of a person-owned protocol; for a `keith`-owned protocol, the instance owner found when the run
  starts (stored on the run, never the literal `keith`). A `keith`-owned protocol names the person of every `wake` and `notify` (`to`);
  there is no implicit owner for a person step. A start with no instance owner is refused (`off`, reason `no-owner`).
- An `act` checks the stored owner of its protocol (`keith` or a person id) against the owner found at its step: a member's protocol
  never runs one; the actor is the owner found at that step.
- `wake` opens the front session of `to` with `frontSessionOptions(id, lock)` and the principal `{ id: to }` (`platform/sessions.ts`), exactly
  as P25's front route does (ADR-0020 §3). Its `billTo` is the run's person when it differs.
- `notify` to a person other than the run's owner is allowed only for a `keith`-owned protocol; a person-owned protocol may notify only
  its owner (no member makes Keith message another member by authoring a protocol).
- A `wake` or `notify` to a suspended or removed person is refused (`person-inactive`), the same rule as P25 (ADR-0027 §15).
- Step outcomes `refused:*` and `failed:*` follow the `failed` branch when there is one; without it and without a `next` the run ends
  `failed`. `refused:budget` with a `next` continues to `next` and tells the person once.

## Budget

`wake` cost is charged to the run (`costUsd`) and reserved from the person's budget as `WAKE_COST_USD` (0.02 USD per turn, a
constant of `steps.ts`; the real turn cost is not known to the engine, and the front route keeps its own check). The person who
pays is the recipient, never the owner by default (P22 cross-cutting rule). A run without budget for one more turn skips the step
with outcome `refused:budget` and tells the person once (a `note`, see `wake` above).

## Authoring (`authoring.ts`, pure)

One function, `authorDefinition({ caller, owner, definition, approve, existing })`, is used by RPC, CLI, agent tools and proposal
confirmation. It returns the parsed definition or a refusal with a reason code. It is table-tested (P28.1.6).

| Who | May create |
| --- | --- |
| Any signed-in person (capability `chat`) | protocols they own with `notify` (to themselves), `ask` (to themselves), `wake` (to themselves), `wait`; triggers `time`, `absence` of themselves, `signal` of their own signals, `event` of their own events (`delivery.failed` with their own `personId`); limits within person caps |
| Person caps | `maxRunsPerDay` at most 5, `budgetUsdPerRun` at most 0.05, `urgent` never |
| Owner only | `owner: keith`; any `act` step; `notify`, `ask` or `wake` to another person; `urgent`; `cancelWhen` over other people; built-ins; limits above the person caps |
| Built-in `owner-absence` only (P29) | `system` steps (`succession.*` actions); the built-in is seeded by the owner role |
| Built-in `dream` only (P35, ADR-0031 §6) | `system` step `dreaming.run` (the dreaming run service of one person). The row is built with `dream-protocol.ts`. The built-in is per person (owner = that person, `syncDream`), not seeded by `keith` |
| Nobody | a step that changes ownership, a grant or a secret. Only the built-in succession protocol of P29 may call `transferOwner` (ADR-0022 §2), through its own coded path, never through `act` |

Refusal reasons: `author-rule` (a step the caller may not author, `FORBIDDEN`), `invalid` (schema path, `BAD_REQUEST`), `needs-approval`
(an `act` without its pre-approval, `PRECONDITION_FAILED`), `unknown-event` (an event type not in the known set), `cap` (a person cap).

Saving an `act` step records the pre-approval. The owner is shown the operation and the exact input (TUI confirm or
`keith-core protocols save --approve`). `protocol_versions.approvals` stores the input hash, never the input in the audit row. Changing the
input is a new version that needs a new approval; a changed input without approval is refused at run time too.

Decisions of the implementation (P28.1.6), each one a rule of the function:

- Input: `{ caller: { id, role, capabilities }, owner, definition, source?: 'protocol' | 'proposal', builtIn?, approve?, existing?: { owner, approvals }, caps: { maxSteps, maxPerPerson, ownedCount }, now }`. The caller holds `chat` (`capabilitiesOf`), else `author-rule`.
- Order: owner gates (keith-owned and other people's protocols are the owner role's; built-ins too; `existing.owner` must equal `owner`), then the definition schema (`invalid`, with the first zod issue path), then the author rules, then the caps (`cap`), then the approvals (`needs-approval`).
- A person-owned protocol names the owner in every person step (`owner-of-run` or the owner's id); the owner role may name another person only in a keith-owned protocol. A keith-owned protocol never uses `owner-of-run` (`invalid`): each step names its person.
- `urgent` is the owner role's; a member's `urgent` is `author-rule`.
- A member's event trigger carries `filter.personId` equal to their own id; a signal or event filter with `person`/`personId` of another person is `author-rule`. Unknown event types are `unknown-event` (the brain event list and `delivery.failed`).
- Conditions: a member may read only their own person (`presence`, `agenda.busy`, `signal.since`, `budget.remaining`, and `cancelWhen`); `approval.pending` is the owner role's. Owner-role conditions are not restricted.
- Person caps (members only): `maxRunsPerDay` at most 5, `budgetUsdPerRun` at most 0.05. The protocol count cap (`protocols.maxPerPerson`) applies on creation only.
- An operation whose name contains `transfer`, `owner`, `grant`, `secret`, `token`, `passw`, `credential`, `role`, `permission` or `capabilit` is refused for every author (`author-rule`).
- A `system` step is refused (`author-rule`, path `steps.N.kind`) unless `builtIn` is `owner-absence` with a `succession.*` action (P29.2.1; `AuthorInput.builtIn` is now the built-in's name, not a flag) or `dream` with `dreaming.run` (P35, ADR-0031 §6: the one action of `dream`). Any other protocol, and any other built-in, is refused.
- Pre-approval: `actApprovalHash(operation, input)` is SHA-256 over canonical JSON (sorted keys) of `{ operation, input }`. A stored approval for the same step and hash is kept; otherwise `approve: true` by the owner role records a new one (`approvedBy`, `approvedAt`); otherwise `needs-approval`. The approvals list holds one entry per current `act` step. Hashing the operation as well as the input means a changed operation is a changed approval.
- A proposal (`source: 'proposal'`) is checked with `ProposalDefinitionSchema` (no `act`, no `urgent`, `owner-of-run` only) and never belongs to `keith`.

Refusal reasons (`AuthorRefusalReason`): `author-rule`, `invalid`, `needs-approval`, `unknown-event`, `cap`; each carries a `path` of the definition.

## Service (`service.ts`, `views.ts`, `removal.ts`, P28.3.1)

`createProtocolService(deps)` is the one place that writes protocols. RPC (P28.3.2) and the CLI call it; the engine does not. It
takes the repos, the settings reader (`maxPerPerson`), an `Audit` and an optional `AclAudit`; it registers nothing itself.

- Calls: `list`, `get`, `save` (no `id`: create; with `id`: a new version, `expectedVersion` is the compare-and-set), `setEnabled`,
  `pause` (`until` epoch ms or `null`), `remove`, `runs`. A protocol keeps the `name` it was created with: another name is
  `BAD_REQUEST`. A stale `expectedVersion` is `CONFLICT` with reason `version`; a duplicate name is `CONFLICT` with reason `name`.
- Every definition goes through `authorDefinition` with the caller as author. The refusal maps to the RPC code: `author-rule` →
  `FORBIDDEN`, `invalid` and `unknown-event` → `BAD_REQUEST`, `needs-approval` → `PRECONDITION_FAILED`, `cap` → `CONFLICT`. The
  reason is carried with the error (`ProtocolError.reason`).
- `enable`, `pause` and `delete` are ownership checks (a member acts on their own protocols; the owner on any). They are not
  definitions, so `authorDefinition` does not run on them. A built-in is paused, never deleted (`FORBIDDEN`, reason `built-in`).
- Visibility: a member sees and changes their own protocols and reads their own runs; an absent or foreign protocol is `NOT_FOUND`.
  A member asking for another person's runs gets an empty list. The owner sees every protocol, `keith`-owned ones included, and
  every run. An owner read of a member's protocols or runs writes `acl.owner-access` with `kind` `protocol` or `protocol-run`
  (one line per window, ADR-0015).
- Pre-approval: `save` with `approve: true` records the approval of each new `act` hash (the owner role only). The `approve` flag
  over TCP needs a step-up (checked in the procedure, P28.3.2). `protocol.approve` carries the hash, never the input.
- Audit rows of a person's protocol carry `subject` (the owner's id): `protocol.create`, `protocol.update`, `protocol.delete`,
  `protocol.pause`, `protocol.resume`, `protocol.approve` are in `AUDIT_SUBJECT_FIELDS` and have an `audit.mine` line, so the member
  sees a change the owner made to their protocol. `keith`-owned rows have no subject.
- Caps: `maxPerPerson` is read from the settings at each call and counted on create only. `maxPerPersonRunsPerDay` belongs to the
  engine's start.

RPC (`procedures.ts`, P28.3.2): `protocols.list`, `get`, `save` (create without `id`, a new version with `id`; the spec's one
save procedure, not separate create and update), `setEnabled`, `pause`, `delete`, `runs`, all `chat` (the service decides the
owner-only parts).
`protocols.answer` (`chat`, no step-up; input `ProtocolAnswerInputSchema`, output `ProtocolAnswerOutputSchema`): answers the open `ask`
of a run. The handler checks first that the run exists and that its person is the caller: another person's run, and the owner's
answer to a member's question, are `NOT_FOUND` (one principal per run, ADR-0020 §2). The engine's `answer` (the same call as the agent's
`protocol_answer` tool) then refuses a closed question with `CONFLICT` (`reason` `not-waiting` or `not-open`), an option the question
does not offer with `BAD_REQUEST` (`reason` `bad-option`). A free text is stored on the run's answer row (the run needs it) and never
written to the audit log: the row `protocol.answer` (`runId`, `subject`, `kind` `option` or `text`) is the only record of it. `save` with `approve: true` over TCP needs a step-up (`STEP_UP`, checked in the handler, not in the metadata).
A refusal is the RPC code of its `ProtocolError` with `data: { reason }` (`reason` is null when there is none). The contract's
metadata lists these procedures; the client reads them through its typed `rpc` (no client method is added). The proposal
procedures (`protocols.proposals`, `confirm`, `dismiss`) are P28.3.4.

Removal (`removal.ts`, ADR-0027 §26): `hypothalamusRemoval({ sqlite, dataDir })` registers as `hypothalamus` in the removal registry
(the composition does it). `stop` disables the person's protocols and cancels their `running` and `waiting` runs before anything is
kept. `keep` writes `hypothalamus.json` (the person's protocols with versions, runs with steps, proposals, agenda items) into the
kept folder; the live rows stay until the keep time, as parietal does. `export` copies that file for a removed person, or writes
the live rows for a present one. `purge` deletes runs and steps, proposals, agenda items and then the protocols (versions go by
cascade); a protocol of another person is untouched.

## Proposals (`proposals.ts`)

Keith may only **propose**. Tool `protocol_propose` writes `protocol_proposals`; it cannot write `protocols`. The proposal shows as a card
in the person's chat and in `Apps > Protocols`. Confirming is a person action (`protocols.confirm`, or answering the card): it re-validates
the stored definition with `authorDefinition` as the confirming person, then creates the protocol. A confirm by another person is
`NOT_FOUND`. An expired proposal (7 days) cannot be confirmed; the prune tick marks it `expired`. Dismiss sets `dismissed` and never
re-proposes the same `(person, source)`.

Decisions of P28.3.4 (`proposals.ts`, over the service's `createProtocol`):

- `propose(caller, { definition, reason, source })` is the one write of a proposal; the tool `protocol_propose` (P28.4.1) calls it.
  The definition is checked by `authorDefinition` with `source: 'proposal'` and the caller as owner, so a proposal never holds an
  `act`, `urgent`, a step to another person or a `keith` owner. The reason is 1 to 200 characters (`BAD_REQUEST`, reason `reason`).
  The owner's cap is checked here too, so a suggestion the person could not confirm is not stored.
- A dismissed `(person, source)` makes `propose` `CONFLICT` with reason `dismissed`.
- `confirm` is `NOT_FOUND` for another person's proposal. A pending proposal past `expires_at` is marked `expired` and refused
  (`CONFLICT`, reason `expired`); a proposal that is no longer pending is `CONFLICT` with its status as the reason. The definition
  is checked again with the confirming person as author; a refusal (for example the cap) leaves the proposal pending. The
  protocol's name is the reason (48 characters at most) and the last six characters of the proposal id, so two of one reason stay
  distinct; the protocol is enabled and version 1.
- `dismiss` on a non-pending proposal is `CONFLICT`. Both writes are audited (`protocol.proposal.confirm`, `protocol.proposal.dismiss`
  with `subject`).
- `protocols.proposals` lists the caller's own proposals only (the owner does not read a member's suggestions); a read marks the
  pending ones past expiry as `expired` first. The prune tick (`compose-timers.ts`) does the same for every person.
- RPC: `protocols.proposals`, `protocols.confirm`, `protocols.dismiss` (`chat`). There is no RPC to propose: a proposal comes from the
  front agent only.

## Agent tools (`tools.ts`, P28.4.1)

Four protocol tools (plus the three agenda tools of the "Agenda" section) of the front agent only (`createFrontAgent` option `protocolTools`; never a worker, a guest or a room). Each runs as
`ctx.principal`, resolved through `AclActors.of` now: the person is never an argument, and a principal that is unknown, suspended
or not a user is refused (`no-person`). A refusal is an answer `{ ok: false, reason, message }`, not a thrown error.

- `protocol_propose({ reason, definition })`: `ProtocolService`'s proposal `propose` with the turn's person as caller; the definition
  is `ProposalDefinitionSchema` (no `act`, no `urgent`, `owner-of-run` only). It writes a `protocol_proposals` row and never a
  `protocols` row. Source: session id and turn id. The answer says the proposal waits for the person.
- `protocol_list()`: the person's own protocols (`id`, `name`, `enabled`, `pausedUntil`, `version`) and their pending proposals.
  Read through the repos, so the owner's read of another person's rows is not made here.
- `protocol_pause({ id, until? })`: own protocols only (`NOT_FOUND` otherwise). With `until` (ISO 8601) it is `service.pause`; without
  it the protocol is switched off (`service.setEnabled(false)`), since a pause has an end.
- `protocol_answer({ runId, option?, text? })`: the run must be the person's own (`run.person`); then `engine.answer` with the person as
  `by`. Free text is passed on and never returned or logged.

Wiring: the front agent is built before the services and the engine exist, so the tools read a slot (`protocolToolSlot`) at call time.
`wireEdge` (`compose-regions.ts`) binds the service, the proposals and the repos; `createProtocols` (`compose-protocols.ts`) binds the
engine, the run and protocol repos. A call before both binds answers `unavailable`.

## Agenda (`agenda.ts`)

Code: `agenda.ts` (`createAgendaService`, `agendaOverlay`, P28.5.1 to P28.5.4); tools in `tools.ts`; procedures in `procedures.ts`;
the front prompt rule `AGENDA_INSTRUCTIONS` in `wernicke-broca/agent.ts`; the table is `agenda_items` (repo `agendaRepo`).
Tests: `agenda.test.ts` (service, proposal, overlay, retention), `tools.test.ts`, `apps/core/src/agenda-extraction.e2e.test.ts`
(scripted front model: a clear time is stored `confirmed`, a vague one stores nothing before the answer), and
`apps/core/src/protocols-leak.e2e.test.ts` (P28.5.5).

- The front prompt block (`AGENDA_INSTRUCTIONS`, added when the protocol tools are wired): when the person states something they
  will do at a time or place, call `agenda_add` with the time they said, as `confirmed` when the time and the meaning are clear. When
  the time or meaning is unclear, ask one short question first and call the tool only after the answer; an item the person has not
  confirmed is `tentative`. Never invent a time; a relative day is resolved with the `datetime` tool. Same turn, no extra model call
  (ADR-0025 consequences).
- Tools (the front agent only, as the protocol tools): `agenda_add({ what, startsAt, endsAt?, place?, status })` (ISO 8601 times;
  the end is later than the start, else `bad-time`), `agenda_list({ from?, to? })` (default now to seven days ahead), `agenda_done({ id })`.
  Each runs as `ctx.principal`; no argument names a person. `agenda_add` stores with `source_session` (the session id) and
  `source_message` (the turn id).
- Service: `add`, `list`, `done`, `cancel`. `done` and `cancel` take an own item in `tentative` or `confirmed` (another person's or
  an absent one is `NOT_FOUND`; a changed one is `CONFLICT` with its status as reason). A member's `list` with another person is
  empty; the owner's `list` with `person` answers that member's items and writes one `acl.owner-access` row (`kind` `agenda`, ADR-0015).
  The agenda writes no `agenda.*` audit row (the owner's reads are audited as above).
- Meeting proposal: a confirmed item that is a meeting (a `place`, or the word "meeting" in `what`) gives one "keep quiet" proposal,
  stored by the proposal service (`propose`, so the definition is checked as a proposal: no `act`, `owner-of-run` only). Its source
  is `{ session, message: 'agenda:<item id>' }`, which is the one-per-item key (a proposal already stored for it, in any status, holds);
  a dismissed source is never proposed again (the proposal service's rule). The definition: a `time` trigger at `startsAt` minus
  5 minutes; one `notify` to `owner-of-run` with the fixed text "Your meeting starts at HH:MM. Keith keeps HH:MM to HH:MM quiet.", the
  times read in the core's zone; reason "keep HH:MM to HH:MM quiet". No proposal when that trigger time is not in the future. A refusal
  (the protocol cap, a dismissed source) leaves the item stored and gives no proposal. The tool answer carries the proposal id and
  reason, so Keith says it in the same turn. Confirming creates a `time` protocol through the proposal service.
- Presence overlay: `agendaOverlay({ agenda, timeZone })` has id `agenda` and `busy(personId, at)`; it is registered with
  `parietal.addOverlay` in `compose-protocols.ts`. It reads `busyAt` (confirmed items only: a tentative item never makes anyone busy).
  The answer is `{ note, until }`: `until` is the latest end of the covering items (an item without an end counts one hour), and the
  note is `in a meeting until HH:MM` when a covering item is a meeting, else `busy until HH:MM`. The note never carries the item's
  text. Disclosure stays parietal's rule; the agenda never writes presence (parietal.md "Ports"). P27's compute is not edited.
- Retention and removal: items are purged 30 days after their end by the prune tick (`repos/retention.ts`, `agendaItems`, P26
  retention); a removed person's items are kept, exported and purged by `removal.ts` (see "Removal").
- Open: no tool or procedure moves a `tentative` item to `confirmed`; a person who confirms a time answers the question and the
  agent stores the item as `confirmed` in the same turn.

## Built-ins (`builtins.ts`, seeded at boot, idempotent by `(owner, built_in)`)

Code: `builtins.ts` (`BUILT_IN_DEFINITIONS`, `seedBuiltIns`), P28.4.2. Seeded by `compose-protocols.ts` at every boot, through
`authorDefinition` (owner role, `builtIn: true`), audited as `protocol.create` (actor `system`, via `local`).

- **No audit row.** A seed is the system installing its own rules, not a person's act, so it writes no audit row (a fresh database would otherwise start with two rows nobody did); an owner's edit, pause or deletion of a built-in is audited by the service as for any protocol.
- **Seed rule.** A built-in that exists for `keith` (any version, enabled or not, paused or not) is never written again: an owner
  edit, pause or switch-off survives every boot, and a second boot seeds nothing. A missing one is created at version 1, enabled.
- **`approval-stale`** (owner `keith`, enabled): trigger `event` `brain.amygdala.wait`, `until: { field: 'expiresAt', beforeMs: 2 h }`
  as seeded (the seeded 2 h is the default of the setting; the engine reads the live `approvals.pingBeforeHours` instead, see
  "Triggers"), guard `approval.pending` (no id: the approval is the trigger's, `approval:<id>`). One run per approval (the trigger ref is
  `approval:<approvalId>`, so a re-read event starts nothing). Step: `notify` to `owner-of-run` with the fixed text "An approval waits
  and expires soon." (no hour in the text: the offset is a setting), then the run ends. The owner-of-run of a keith-owned run is the instance owner (`recipientOf`:
  the self layer reads as the owner, ADR-0020), so the ping goes to the owner role, who answers the approvals of members.
  The guard re-reads the approval's current `expiresAt` at wake time: a later expiry waits again until `expiresAt - 2 h`; an answered
  or expired approval ends the run `skipped`. It never answers or expires anything (ADR-0027 §10, P24).
  The ping offset is `approvals.pingBeforeHours` (default 2 h, amygdala.md) read live: a change applies to the approvals that start
  waiting after it, and a pending ping moves at its wake time (the limit stated in "Triggers").
- **`reminder-missed`** (owner `keith`, enabled): trigger `event` `delivery.failed` with `filter: { source: 'plugin:reminders' }`. The run
  acts for the person of the failed delivery (`personId` of the record, passed as the run's person; one run per `deliveryId`). Steps:
  `wait` 15 minutes, `notify` `owner-of-run` (that person) with the fixed text "A reminder could not be delivered earlier; here it is
  now."; on `failed` the run waits 1 hour and notifies once more, then ends. Queueing for the next connection is the delivery service's
  own retry (P25); the step has no delivery mode of its own.
- **`owner-absence`** is reserved for P29 and not seeded here.
- **`dream`, per person (P35, ADR-0031 §6).** Not seeded by `BUILT_IN_DEFINITIONS`: the built-ins above are `keith`-owned and unique on
  `(owner, built_in)`, while `dream` has one row per person with a mode other than `off`. `syncDream(personId, mode)` in
  `dream-protocol.ts` writes it, idempotently, in the style of `syncOwnerAbsence` (`builtins-succession.ts`): create or enable when the
  mode is not `off`, disable when it is `off`, never delete. Its trigger is `time` `0 3 * * *` in the host zone, its conditions are
  `not(signal.since <person>, 30 min)` and `budget.remaining >= dreaming.maxUsdPerRun`, and its one step is the `system` action
  `dreaming.run` (Authoring above). The sync runs at boot for every person and whenever `dream.mode` changes (`compose-protocols.ts`
  `Protocols.syncDream`). `ProtocolBuiltInSchema` (`packages/contracts/src/protocols.ts`) holds `dream`; `dream` holds `dreaming.run` only.

Authoring rule for these (`authoring.ts`): a keith-owned protocol may name `owner-of-run` only when its trigger is an `event` (the
event names the run's person, or the owner stands in); a keith-owned protocol with a time or other trigger still names a person per step.

A built-in can be paused or switched off, not deleted (`FORBIDDEN`, reason `built-in`). The doctor's `protocols` line (`core-cli.md`)
reads it: a missing or switched-off built-in is a `!` note.

Settings are read from the settings repo, never a literal in the engine. The bounds and defaults of the three `protocols.*` keys are

`settings.read`.

## Audit

Actor is who did it, `via` is the surface (`tcp`, `cli`, `tool`, `system`). Never message text, never the input of an `act` (its hash only).
The `subject` of a run row is the run's person (for a `keith`-owned run, the instance owner found at its start), so the owner sees the
rows of its own keith-owned runs through `audit.mine`.

| Kind | When | Detail |
| --- | --- | --- |
| `protocol.create` | a protocol is saved first time | `id`, `owner`, `name`, `version` |
| `protocol.update` | a new version is saved | `id`, `version`, `from` |
| `protocol.delete` | a protocol is deleted | `id`, `owner` |
| `protocol.pause` / `protocol.resume` | enabled or paused changed | `id`, `until` |
| `protocol.approve` | an `act` pre-approval is recorded | `id`, `version`, `stepId`, `hash` |
| `protocol.proposal.create` | Keith proposes | `id`, `person`, `source` |
| `protocol.proposal.confirm` / `protocol.proposal.dismiss` | a person decides | `id` |
| `protocol.run.start` | a run starts | `runId`, `protocolId`, `trigger`, `status`, `subject` (a person-owned run) |
| `protocol.run.step` | a step outcome is written (`started` is not a row) | `runId`, `protocolId`, `step`, `kind`, `outcome`, `subject` |
| `protocol.run.end` | a run ends | `runId`, `protocolId`, `status`, `reason?`, `subject` |
| `protocol.run.refused` | a start or step is refused | `protocolId`, `reason` (`daily-limit`, `budget`, `person-inactive`, `pre-approval`, `risk`), `subject` |
| `protocol.act` | an `act` reaches its call (P28.2.6, `act.ts`): one row per execution, read or not | `runId`, `step`, `subject`, `node` and `capability` or `plugin` and `operation`, `hash` (`actApprovalHash`); never the input or the output |
| `protocol.answer` | a person answers an open `ask` of their own run (`protocols.answer`) | `runId`, `subject` (the person), `kind` (`option` or `text`); never the text |
| `acl.owner-access` | the owner reads a member's agenda or protocol detail | `kind`, `id`, `owner` (the member), `bits` |
| `settings.protocols.set` | a protocol setting changes | `{ from, to }` (the keys given) |
| `settings.approvals.set` | an approval setting changes (one row per value) | `{ key, from, to }` |

`protocol.*` rows whose subject is a person are visible to that person through `audit.mine` (ADR-0027 §6). The subject is the `subject`
field (`AUDIT_SUBJECT_FIELDS`, `packages/contracts/src/audit.ts`): set for a person-owned protocol, and for every run row (`protocol.run.*`,
`protocol.act`, `protocol.run.refused`), where it is the run's person. The configuration rows of a `keith`-owned protocol
(`protocol.create`, `protocol.update`, ...) have no subject. P28.2.7 registers every `protocol.*` kind there and in `registerMySummary` (`modules/audit/mine.ts`); a test fails when one is
missing. The engine's rows are written by `journal.ts` with actor `system`, via `local`.

## Events

Activity records (`brain.hypothalamus.*`), region `hypothalamus` (`BrainRegionSchema`). Payloads are in `packages/contracts/src/brain.ts`;
`personId` is derived from the session by `emit`, as for every brain event. Emitted on the front session of the run's person: the
person of a person-owned run, and the instance owner found at the start for a `keith`-owned run.

| Event | Payload | When |
| --- | --- | --- |
| `brain.hypothalamus.fire` | `region`, `personId?`, `protocolId`, `runId`, `trigger` (`time`, `absence`, `signal`, `event`) | a run starts |
| `brain.hypothalamus.step` | `region`, `personId?`, `runId`, `step`, `kind`, `outcome` | a step outcome is written |
| `brain.hypothalamus.wait` | `region`, `personId?`, `runId`, `wakeAt` | a run starts waiting |
| `brain.hypothalamus.end` | `region`, `personId?`, `runId`, `status` | a run ends |

No text in any event. Visibility follows the feed filter: a person sees their own; a keith-owned run's events are the owner's. `journal.ts`
adds `region` (the brain payload contracts require it) and writes the record on `front:<personId>`; an event without a person is
reported to `warn` and dropped (the engine always sets one). The payload
contracts (`HypothalamusFirePayloadSchema` and the three others in `brain.ts`) parse every record the journal writes (`journal.test.ts`).

## Errors

RPC codes with the message: `BAD_REQUEST` for an invalid definition (the first zod issue path in the message); `FORBIDDEN` with `reason:
author-rule` for a step the caller may not author; `CONFLICT` for a duplicate name or a stale `expectedVersion`; `NOT_FOUND` for another
person's protocol (as good as absent); `PRECONDITION_FAILED` for an `act` without its pre-approval; `TOO_MANY_REQUESTS` is not used;
caps are `CONFLICT` (`cap` reason).

## Ports (`modules/hypothalamus/ports.ts`)

The engine takes its durable state from the repos (`protocolsRepo`, `protocolRunsRepo`) and everything else through these injected
ports. Each one is an adapter over the owning region; `ports.ts` redefines none of them. The engine (`createEngine`) is built from:

```ts
interface EngineDeps {
  clock: { now(): number; timeZone: string }      // the core's clock and zone
  conditions: ConditionPorts                       // conditions.ts: presence, agenda, lastSign, budget, approvals
  protocols: ProtocolsRepo; runs: ProtocolRunsRepo // the repos (db.md)
  steps: StepRunner                                // notify, ask, wake, act (P28.2.3, P28.2.4)
  journal: Journal                                 // audit(kind, detail) and event(type, payload); the adapter is P28.2.7
  transaction: <T>(fn: () => T) => T               // one write transaction over the core database
  ownerOf: () => Promise<string>                   // the instance owner, read at use (run start, act step, owner notice); '' = none
  warn?(message: string): void
  tickLimit?: number                               // due runs per tick, default 50
}
interface StepRunner {
  run(input: StepRunInput): Promise<StepResult>    // done(outcome) or open(timeoutMs) for an ask
  tell(input: { to; key; text }): Promise<void>    // a keyed notice to a person (the owner of an unknown act)
}
```

`Journal.audit` takes the `protocol.run.*` kinds and `Journal.event` the `brain.hypothalamus.*` types, both with flat details only.
The delivery port (`deliver-port.ts`, P28.2.3) and the node and plugin invoke port (`act.ts`, P28.2.4) are inside `StepRunner`
and are defined in their steps.

The parietal overlay the agenda registers: `PresenceOverlay` of `parietal.md` (`id: 'agenda'`, `busy(personId, now)`), added with
`parietal.addOverlay`. P27's compute is not edited. The `presence` condition reads `disclosedFor` only.

### Plugin port (`host-port.ts`, P28.6.1)

`createProtocolHostPort` implements the port `k.protocols` of `@keith/host` (`docs/specs/plugins/reminders.md`, "Internals"). `upsertTime` stores a protocol of one time trigger and one `notify` or `wake` step, owned by the person the plugin names (never `keith`), named `<plugin>:<key>`, and authored by the caller through `authorDefinition`, so a person-owned protocol messages only its owner (the owner role included). `cancel` removes it for its owner or the owner role. `runEnded(runId, status)` is called by the journal at each `brain.hypothalamus.end`; it tells the `onRunEnd` handlers of the plugin whose protocol the run belongs to (a protocol without a `<plugin>:` name tells nobody). The composition hands plugins a delegating port (`delegatingProtocolsPort`) bound once `wireEdge` has the service; a call before that is refused.

## Invariants

- A protocol never widens access and never changes ownership; its `act` runs with the stored pre-approval and the same checks as a person.
- A text is never templated; the model is called only by a `wake` step; the engine never calls a model.
- A `(protocol_id, trigger_ref)` run starts at most once; a delivery key `<runId>:<stepId>:<visit>` is sent at most once.
- A model context (of any turn) holds protocols, runs, proposals and agenda items of its own principal only (ADR-0020 §2).
- Keith cannot create a protocol: only a proposal, confirmed by a person.
- An `act` is never repeated after a crash; it becomes `unknown` and the owner is told.
- Idle engine cost: zero queries beyond the due-run check.
